# 领域优先的技术博客写作

## 目标

写出一篇**先是一篇有用的技术文章，其次才是一篇软件介绍**的博客。

读者读完后应当知道：

1. 这个方法在解决什么科学问题；
2. 公式中的每个量来自什么物理状态或计算；
3. 原始方案已经解决了什么，实际使用还缺什么；
4. 新工具如何把理论要求落实成一组计算任务；
5. 新工具真正增加了哪些能力，以及这些能力为什么对结果或使用过程有意义。

不要把文章写成：

- 软件手册；
- DSL语法教程；
- 对任务图/DAG本身的宣传；
- 修改过程或对话要求的回声；
- 为证明软件先进而堆积功能名词的产品文案。

## 核心原则

### 1. 领域问题是主线，工具只是解法的一部分

文章的叙事顺序应由科学问题决定，而不是由软件模块、配置项或代码文件决定。

优先顺序通常是：

**问题 → 原理 → 所需计算量/参考态 → 原方案如何得到这些量 → 原方案的实际缺口 → 新工作流如何覆盖这些量 → 新增能力**

判断标准：把软件名从正文中暂时删掉，前半篇仍应是一篇成立的技术解释；把软件名放回来以后，后半篇应自然回答“为什么值得用它”。

### 2. 图表达计算关系，正文解释理论关系

当任务图、流程图或DAG已经画出后，**不要再把图本身当成文章主题**。

允许：

- “计算流程如下。”
- “虚线部分只在启用溶剂模型时出现。”
- “最前面的复合物和ghost片段给出……”。

避免：

- “这种问题非常适合直接看DAG。”
- “把同一流程写成DAG后，计算关系会清楚很多。”
- “从DAG上看，这套计算非常适合并行。”
- “这个DAG和物理定义一一对应。”

图的价值应由内容自己体现。正文应回答的是：

- 这个节点计算什么物理量？
- 为什么需要这个参考态？
- 哪些能量做差得到目标量？
- 打开某个方法选项后，需要增加哪些计算？
- 参考态是否随目标量改变？

**图是论证工具，不是被论证对象。**

### 3. 宣传工具能力，但宣传“能力结果”，不要宣传“形式”

技术博客可以宣传软件，而且应该把真正有价值的部分讲清楚。但宣传必须形成完整因果链：

**底层能力 → 工作流行为 → 用户获得的结果**

例如：

- 独立任务状态 → 某个单体优化失败只阻塞依赖它的结果 → 已完成任务不必重跑；
- 条件任务分支 → 开启形变能时自动增加自由单体优化 → interaction energy自动扩展为binding energy；
- 参考态随分支选择 → 开启形变能后溶剂热力学循环自动使用自由单体 → 不需要用户手工维护两套公式；
- 独立溶剂分支 → 保留真空EDA定义，同时额外给出连续介质修正 → 扩展原脚本未覆盖的方法能力；
- 中间物理状态显式任务化 → detail输出只改变结果整理 → 不必为了报告更多分量重复量化计算。

不够好的宣传：

- 图更漂亮；
- DAG更清楚；
- 更现代；
- 更优雅；
- 更适合并行；
- 代码更容易读。

这些描述即使成立，也不是科研用户最关心的价值。用户关心的是**算什么、少做什么手工操作、哪里能自动扩展、失败以后要不要重算、参考态会不会选错**。

### 4. 用理论量组织任务，不用DSL组织文章

介绍工作流时，任务名称应尽量对应领域对象：

- 复合物气相单点；
- ghost片段；
- 自由单体优化；
- frozen state；
- 溶剂单点；
- 形变能；
- 最终结合能。

正文不应按下面的实现概念展开：

- `%source`如何传结构；
- `@derive`如何聚合；
- `@foreach`如何展开；
- 文件如何命名；
- parser读取哪个字段；
- 内部action如何调用另一个库。

除非文章本身就是“如何编写该DSL”，否则这些内容属于实现文档，不属于方法博客。

配置名也只在它本身是用户需要操作的入口时出现；即便出现，也先解释它改变了哪个理论分支，再给名字。

### 5. 原方案是基线，不是陪衬或靶子

介绍原脚本/原程序时，要准确说明：

- 它已经自动完成哪些步骤；
- 它默认如何处理关键中间态；
- 哪些功能需要额外操作；
- 哪些限制会在实际任务中产生麻烦。

不要为了突出新工具而贬低原方案，也不要把原方案拆成逐行代码审计。

好的写法通常是：

> 原脚本已经把片段计算、promolecule构造和最终能量分解串起来，用起来并不复杂。不过它仍是一条Shell流程，各计算步骤没有独立任务状态，连续介质溶剂也不在原流程内。

这里同时完成三件事：承认原方案有效、指出结构性限制、自然引出新工具。

### 6. 新能力必须回到理论定义上解释

功能不是列表。每个重要能力都应回答：**它改变了哪一个理论量的获得方式？**

例如形变能不是“多了一个deformation开关”，而是：

1. 目标从固定构型相互作用能扩展到结合能；
2. 因此需要复合物构型单体和自由单体两套参考态；
3. 因此新增自由单体优化与单点；
4. 溶剂修正的参考态也必须随之切换；
5. 工具应自动维护这些依赖和参考态选择。

这比介绍一个布尔参数更能体现软件价值。

### 7. 允许不对称，按“解释价值”分配篇幅

人类作者不会为了格式整齐，把每个模块都写成同样长度。

某个公式只有一步，就一两段讲完；某个参考态容易混淆，就多解释一些；某个实现细节虽然代码很多，但读者不需要知道，就删掉。

不要机械追求：

- 每节三个小标题；
- 每个功能一段“优势”；
- 每张图后固定四点说明；
- 每种开关都做表格；
- 每篇文章都以“总的来说”收尾。

篇幅分配由读者理解成本决定，而不是版式对称决定。

### 8. 作者可以有判断，但判断必须落地

技术博客需要作者声音。好的作者判断往往是具体、可验证、与实际使用相关的，例如：

- “CP公式本身并不复杂，真正容易麻烦的是后面这些参考态。”
- “原脚本已经能完成真空sobEDA，新增价值主要在任务状态和额外物理分支。”
- “只算相互作用能时没有必要优化自由单体。”

这种句子比“该方案具有很高的灵活性和可扩展性”更像人写的，因为它体现了取舍和经验。

判断后应尽快给机制或例子，不要只发表态度。

### 9. 只保留读者需要的实现层级

技术博客和开发文档的区别不是“有没有代码”，而是**代码是否承担解释功能**。

保留代码的条件：

- 它是原方法的标准入口；
- 它是用户真正需要改的关键参数；
- 它能比 prose 更短地说明输入形式；
- 它直接帮助读者复现实验或理解方法边界。

删除代码的条件：

- 只是证明实现确实存在；
- 只是展示内部DSL能力；
- 与理论量没有直接对应；
- 读者不需要修改或理解它；
- 图和一句话已经能说明同一件事。

### 10. 软件价值应从“原方案缺口”自然长出来

不要先决定要夸什么，再去正文里找证据。先列出原方案在实际任务中的缺口，然后只宣传新方案真正填上的部分。

常见缺口包括：

- 计算步骤只有流程顺序，没有独立状态；
- 失败后重跑范围过大；
- 可选理论项需要手工增删计算；
- 多套参考态需要手工维护；
- 原脚本没有覆盖溶剂、形变、热校正等扩展；
- 报告需求改变会触发重复计算；
- 多片段扩展需要手工复制逻辑。

如果新方案没有解决某一项，就不要写。

## 推荐结构

### A. 开头：问题与方法定位

用1–3段说明：

- 为什么要算这个量；
- 直接做法哪里有问题；
- 本文方法解决哪一层问题。

不要在开头列“本文将介绍……”目录式提纲。

### B. 原理：先定义量，再定义计算状态

顺序通常是：

1. 定义总量；
2. 引入造成差别的物理状态/参考态；
3. 给关键公式；
4. 解释每个量的物理含义；
5. 只补真正会影响后续工作流的边界。

### C. 原方案：讲它如何实现理论

只写与后文比较有关的内容：输入、关键步骤、关键开关、原方案未覆盖的部分。

不要把原脚本全文翻译成中文。

### D. 新工作流：先放图，再沿理论量读图

图后按目标量说明：

- 哪些节点给相互作用能；
- 哪些节点给形变能；
- 哪些节点给溶剂修正；
- 哪个选项会改变参考态；
- 哪些结果最后汇合。

随后才介绍task级控制带来的行为：状态、等待、局部重算、条件分支等。

### E. 收尾：总结新增的方法能力

结尾不要再次复述整篇理论。回答：

- 原方案已经做到什么；
- 新工具额外自动处理了什么；
- 为什么这些增量对实际计算有意义。

## 写作工作流

### 第一步：建立“理论量—计算任务”表

内部整理，不必原样输出：

| 理论量 | 需要的能量/状态 | 对应计算 | 是否可选 | 参考态是否会切换 |
|---|---|---|---|---|
| interaction energy | ... | ... | 否 | 否 |
| deformation | ... | ... | 是 | 是 |
| solvent correction | ... | ... | 是 | 可能 |

如果这个表还没有理清，不要开始写软件部分。

### 第二步：建立“原方案—新方案差异”表

只记录用户可感知的能力差异：

| 问题 | 原方案 | 新方案 | 用户收益 |
|---|---|---|---|
| 失败重算 | ... | ... | ... |
| 形变能 | ... | ... | ... |
| 溶剂效应 | ... | ... | ... |
| 参考态选择 | ... | ... | ... |

不记录类名、函数名、parser、内部数据结构，除非文章主题就是实现。

### 第三步：先写不含软件名的原理段

检查这部分是否独立成立。如果原理必须靠软件术语才能解释，说明叙事层级混乱。

### 第四步：写原方案，建立真实基线

避免“旧方法很麻烦”这种空话。指出具体缺口。

### 第五步：画任务图

节点用领域名称，不用内部对象名。边表示真实依赖；可选分支用视觉差异表达。

### 第六步：沿公式解释图

禁止逐边念图。只解释公式需要的计算量如何在图中获得，以及选项改变哪一组参考态。

### 第七步：补工具优势

每个优势必须通过下面句式审查：

> 因为系统能够 ______，所以当 ______ 时，用户不需要 ______，最终可以 ______。

如果填不完整，通常说明这只是口号。

### 第八步：做“对话泄漏”审查

删除所有可能来自写作指令而不是文章主题的句子，例如：

- “这里适合用DAG解释”；
- “按前面的要求”；
- “这一版”；
- “为了展示BaneTask的优势”；
- “下面不讲实现细节”；
- “这里重点介绍task级控制”。

作者应像从一开始就知道文章该怎么写。

## 快速判废标准

出现以下任一项，应重写对应段落：

- 正文评价任务图“清楚、漂亮、直观、适合并行”，但没有说明具体计算能力；
- 用户要求“用图解释”后，正文突然反复出现DAG/流程图等词；
- 软件部分按DSL关键字、模块、函数或文件结构组织；
- 用大段代码证明工具能力，却没有说明它改变了哪个理论量；
- 把“支持某开关”当成优势，而没有解释开关对应的参考态和结果变化；
- 只说“可以自动化”，不说自动化了哪些原本需要手工维护的计算；
- 原方案被刻意写得笨拙，只为衬托新工具；
- 删除软件名后，文章前半部分不能独立解释方法；
- 删除图以后，正文只剩“这个节点到那个节点”，不能解释公式；
- 删除代码以后，文章就失去主要内容；
- 每个小节篇幅、句式和结构过度对称；
- 出现“更清晰、更优雅、更现代、更灵活”等无法从具体工作流验证的宣传词；
- 正文暴露修改过程、用户反馈、旧版本反驳或内部实现视角。

## 三个最终测试

### 领域测试

随机选一段，问：这段首先是在讲科学问题，还是在讲软件自身？除软件章节的必要段落外，答案应以前者为主。

### 能力测试

对每一句软件优势，问：它是否能对应到一个具体任务行为、参考态变化、失败恢复行为或新增物理计算？如果不能，删掉或改写。

### 作者测试

问：这篇文章是否体现了作者知道“哪里真正麻烦、哪里不值得展开、哪些能力值得强调”？如果只有完整，没有取舍，就仍然像自动生成的说明文。

## 与 avoid-ai-flavor-writing 的关系

本技能解决的是**技术博客的叙事方向和能力表达**；`avoid-ai-flavor-writing`解决的是引号、元话语、历史痕迹、防御性措辞、标题尺度等通用AI味问题。

推荐同时启用。优先级为：

**技术事实正确 > 领域叙事正确 > 能力宣传有因果 > 作者取舍 > 去AI味表面审查 > 文风修饰。**
